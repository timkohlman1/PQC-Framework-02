IMPLEMENTED REQUEST-16 ARCHITECTURE

The authoritative run-evidence schema is now `pqc-run-evidence` schema version 3. Its responsibility is run capture and provenance, not scientific result interpretation.

The execution framework is responsible for:
- resolving and snapshotting the exact experiment case before side effects;
- recording source/dependency/tool/build/preparation/deployment provenance;
- orchestrating execution and recording only completion/end-point/failure state needed to say what ran;
- collecting raw artefacts;
- assigning extensible semantic roles/source classes;
- recording result-relative path, producer stage/tool, size and SHA-256;
- recording required/optional/not-applicable capture requirements and acquisition status;
- re-hashing raw files at finalisation and sealing an immutable capture index; and
- recording whether the required raw capture package is complete/integrity-valid.

It is explicitly NOT responsible for interpreting scientific measurements into the authoritative run manifest. Timing, memory, TLS/security-function/primitive, energy, packet-level and benchmark values remain in raw structured records/logs until a separate ingestion stage parses them.

The main schema-v3 concepts are:
- `resolved-case.json`: immutable non-secret resolved-case snapshot, including profile identities/content hashes, resolver/schema version, configuration identity, firmware identity and effective non-secret parameters; secrets remain excluded and only named secret references/public identities are retained.
- `capture_contract`: minimum raw artefacts required by the resolved experiment class/features.
- `artifacts`: extensible raw-artefact inventory using a stable common envelope rather than a closed metric schema.
- `execution_outcome`: orchestration/SUT completion state only (for example completed, failed, not executed or not applicable, plus failure/completion basis). It is not a scientific validity judgement.
- `capture_acceptance`: whether every capture-contract-required raw artefact was retained and passed integrity checks. It does not claim every metric is present, parseable or scientifically valid.
- `final_index`: immutable digest over the run-capture/provenance state. Scientific derived outputs are deliberately excluded from this digest.

At finalisation the framework aggressively compacts the root manifest. Verbose runtime/stage/metric payloads used during execution are removed from `manifest.json`. Reproducibility/deployment metadata is snapshotted once to hashed `run-provenance.json`. Semantically important contract artefacts remain in the richer `artifacts` index; every other retained run file is listed once in compact `retained_files` records containing only result-relative path, byte size and SHA-256. The inventory excludes `manifest.json`, mutable manual notes and the later `analysis/` namespace.

Raw evidence remains immutable after collection. Examples include STM32 structured result streams, diagnostic UART, broker/observer logs, PCAP/TLS key logs, secure-boot/OTA records, ESP32 energy traces and future benchmark records.

DERIVED/INGESTED OUTPUTS

Scientific parsing, normalisation and analysis occur after capture. Derived outputs must not reopen, mutate or reseal the finalized run manifest.

Derived/ingested outputs should live under a result-local analysis namespace (for example `analysis/`) with separate lineage records containing:
- parser/analyser/tool identity and version;
- direct input artefact SHA-256 identities;
- relevant analysis/ingestion parameters;
- output size; and
- output SHA-256.

Re-running ingestion or analysis may create/update derived outputs and lineage while the original run manifest and raw artefacts remain unchanged. This is intentional: improved parsers should be able to reprocess historical physical experiments without rerunning the hardware.

The conceptual pipeline should therefore be described clearly as:

resolved experiment
→ build/deploy/execute
→ immutable raw capture + provenance manifest
→ ingestion/parsing
→ normalised observations/dataset
→ analysis/aggregation
→ thesis figures/tables

Do not collapse capture acceptance and analytical validity into a single status.

AGGRESSIVE MANIFEST COMPACTION IMPLEMENTED IN REQUEST 16

The finalised root `manifest.json` is now intentionally a compact index rather than a persistence location for every stage payload. The thesis must make the following distinction explicit:

- transient execution state may temporarily contain detailed stage structures while the framework is orchestrating a run;
- finalisation snapshots durable reproducibility/deployment metadata into `run-provenance.json`;
- the final root manifest keeps only schema/run/configuration identity, capture contract, execution outcome, capture acceptance, semantic artefact entries, compact retained-file hashes and final-index sealing data;
- parsed UART/TLS/memory/secure-boot benchmark values and verbose broker/flash/stage dictionaries are not retained as authoritative root-manifest content;
- later ingestion obtains scientific observations from immutable raw files, not from legacy metric branches in the run manifest.

Do not describe `run-provenance.json` as a scientific results file. It is a reproducibility/deployment provenance sidecar and is itself hashed by the run manifest.
